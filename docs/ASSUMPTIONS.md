# Product decisions — current cloud edition

- The owner's Firebase request supersedes the original browser-only/offline-writes requirement. All primary shop records, settings, catalogs, users/roles, expenses and audit history live in Firestore. Only the PWA shell, Firebase login persistence and a server-confirmed memory view remain client-side conveniences. Offline financial writes fail explicitly.
- One Firebase email/password account owns one shop at shops/{uid}. New device/browser login uses the same account and does not create another manager. Create/use options are Arabic to preserve the app language. Owner display name initially uses the email and can be changed in settings.
- Staff users remain within the owner-authenticated session, preserving existing permissions and PBKDF2 hashes. They do not become separate Firebase owners. Switching a local role locks the UI; logging out signs out Firebase. Firebase auth restoration selects the existing owner on reload.
- Password recovery for the Firebase owner uses email, not the old offline code. Old manager passwords or recovery codes authorize optional legacy migration. The original browser data is not silently uploaded into an arbitrary shop and is not erased. Existing JSON backups can be restored after owner sign-in.
- Restore rebinds a valid owner record to the signed-in Firebase UID, keeps historical user references and disables foreign Firebase-owner placeholders. Firebase login credentials/tokens never come from a backup. Staged generations prevent partial replacement; a concurrent cloud edit cancels restore for review. Old generations remain owner-protected rather than deleting financial history.
- Cloud data preserves explicit record order, immutable closing snapshots, app version 2.0.0 and logical schema version 2. Large records use bounded UTF-8/base64 chunks. Delta logs avoid rereading the entire history on every action; cloud memory is never accepted as current without a server revision check.
- All settings, including the existing device label, are shared shop settings. Cloud does not create a different ledger per device. Logo uploads are resized to at most 512px JPEG to keep the shared settings document bounded.
- Default rates/room counts, catalogs, Cairo timezone, visual palette and integer money rules remain the same. No pruning is introduced. Timers still derive from stored epoch timestamps.

- The confirmed thresholds are 35 and 45 in defaults and session pricing. **49 minutes bills 60, not 45.** The explicit table supersedes the conflicting original example. Zero minutes bills 30 with rounding on, zero with it off. Elapsed minutes are floor(milliseconds / 60,000).
- Currency inputs use Western digits and at most two decimals, parsed into integer piasters. Percentage inputs use basis points: 10.25% is 1025. Percentage discounts round fractional piasters upward and cap at subtotal. Exact-price mode also rounds fractional piasters upward. Other price modes round the play charge upward to 50 or 100 piasters, once per session. Conversion to fractional pounds happens only for display/export.
- Fixed discounts cap at subtotal; percentages above 100% are rejected. Zero service prices and zero bills are allowed. Expenses must be positive. Negative amounts are rejected.
- **Gross play revenue** = finished sessions' play charges. **Gross services revenue** = their service charges. **Discounts** = their discounts. **Net = gross play + gross services - discounts - nonvoided expenses.** Discounts are subtracted once. **Unpaid = sum(max(total - paid, 0))**; revenue counts the full bill. Change is max(paid - total, 0).
- Running sessions show provisional accrual but are excluded from finalized totals, services sold and finished counts. Cancelled/voided sessions contribute zero and appear separately. Finished counts include underpaid sessions, with unpaid shown separately. Room ranges include audit records for traceability.
- Closing is blocked until all running sessions are ended or cancelled; the dialog opens each session to do either. Closed shifts are immutable, including expenses and sessions. Thus voiding a finished session is permitted only during its open shift. There is no reopening. Closing snapshots settings, logo, user names, sessions, expenses and totals. The three report layouts are described below.
- A shift belongs to its start date in the configured timezone, even across midnight; later timezone changes do not regroup it. The datetime input uses the device's native timezone. Reports use stored timezone names.
- Start time cannot be future or before shift opening. Native inputs have minute precision; leaving the default unchanged starts at the actual confirmation timestamp. Explicit edits use the entered minute and are rejected if before shift opening. Editing a running session requires editSessionTime. Checkout captures its end timestamp on opening payment, so typing does not increase the bill; reopening checkout captures a new end.
- No server clock correction exists. Backward clock jumps clamp provisional displays to zero; ending before start is rejected. Forward jumps increase the bill. Fix the device clock or use authorized time editing. Wall-clock idle lock can also be affected by clock adjustments.

## Reports and export revision

- Exactly three tabs remain: inclusive date-range totals, daily shift rows, and live/final shift detail. Totals show play, services, discounts, expenses, net, shift count. Daily rows now show name, from, to, revenue, expenses, net. Revenue means play + services - discounts; net additionally subtracts expenses.
- The detail tab defaults to the open shift, and closing deep-links the exact frozen shift, even across midnight. Sessions are clean tappable summaries; the modal exposes the complete fields. PDF prints all details even while the screen list is collapsed. Empty optional fields are omitted.
- The new shift Excel request supersedes the old identical-card export: a small summary (shop, shift, period, play, services, discounts, expenses, net) precedes one 12-column session table in the requested order. It has cached subtotal results, borders, sized columns, a frozen header and real Excel date/money formats. Dates use stored shop/session wall-clock time. Other report exports keep their compact summary/list formats.
- Cancelled/voided rows remain for audit, include their status in the room text, and contribute zero to numeric session-table totals. Running rows are provisional and show no finalized paid/change. The top financial summary is finalized revenue; an explicit live note explains provisional rows below.
- Firebase rules/provider/domain publication is a manual owner step. The supplied public config permits SDK use but not Console administration. The existing project public config was verified to lack the GitHub Pages authorized hostname; add it before production use.
- The current source remains public and deploys through the existing Pages workflow. Production and emulator builds use separate directories; a guard rejects demo Firebase project strings in the deployed build. No emulator/test account is created in production during automated validation.
